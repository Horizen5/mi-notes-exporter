# 私密笔记的加密原理

小米便签的「私密笔记」不是靠密码加密的，靠的是一把**存在手机里的随机密钥文件**。你输的那个隐私密码只决定界面能不能进这个文件夹，跟密文一点关系都没有。

这份文档把实测出来的参数、推导过程和验证方法写全，换设备 / 换系统版本时可以照着复核。

---

## 1. 数据放在哪

MIUI 和 HyperOS（澎湃 OS）都用同一个包名，路径完全一样：

```
/data/data/com.miui.notes/
├── databases/
│   ├── note.db                  ← 主库，780 行 note + 1116 行 data
│   ├── note.db-wal              ← 最近改动还没落盘的部分
│   ├── todo.db                  ← 待办
│   └── dbpref.db                ← 界面偏好
├── files/
│   ├── miui_notes_secret_2      ← 32 字节，私密笔记的密钥
│   └── attachment/              ← 图片，文件名是 40 位 sha1
├── shared_prefs/                ← 只有字体/排序/同步时间，没有密码
└── cache/                       ← 可丢
```

`/data/data` 下每个应用的目录权限是 `drwx------`、owner 是该应用自己的 uid（本机实测为 `u0_a237`），而 adb shell 跑在 `uid=2000`，所以**不 root 读不到**。`run-as com.miui.notes` 也不行，因为小米便签不是 debuggable 版本，会直接报 `package not debuggable`。这也是为什么这个仓库有两种方式：普通用户走浏览器扩展读云端，有 root 的直接读库。

## 2. 加密参数

全部实测，不是猜的：

| 项目 | 值 |
|---|---|
| 算法 | AES-256-CBC |
| 填充 | PKCS7 |
| 密钥 | `files/miui_notes_secret_2` 的 32 字节**原文**，直接当 key |
| 密钥派生 | **没有**，不经过 PBKDF2 / SHA / MD5，也不是密码哈希 |
| IV | `fc9710a048cd7a2e775396ee4280face`，16 字节固定值 |
| 密文位置 | `data.content`，字段类型是 TEXT，内容是 Base64 |
| 第二份密文 | `note.plain_text` 里**也是密文**，两个字段都要解 |

Base64 是带换行的（每 76 字符左右一个 `\n`），解码前要先去掉空白：

```python
s = re.sub(r"\s+", "", blob)                       # 去掉换行
raw = base64.b64decode(s + "=" * (-len(s) % 4))    # 补齐 padding
```

解出来的是**明文 XML**，和普通笔记的正文格式一模一样（`<text indent="1">…`、`<img fileid="…"/>`），所以解密之后可以直接套用同一套渲染逻辑。

---

## 3. 为什么说不用密码

三条独立的证据，任一条成立就够了：

**① 数据库里没有任何密码字段。** 整个库只有 `account`、`note`、`data`、`android_metadata`、`sqlite_sequence` 五张表，按 `pass` / `lock` / `pin` / `key` / `crypt` 扫过全部列名，零命中。连密码的哈希都没存。

**② 偏好设置里也没有。** `shared_prefs/com.miui.notes_preferences.xml` 里只有 `pref_key_font_size`、`pref_key_note_sort_way`、`SyncWindowStart_notes` 这类东西。私密文件夹那一行（`note._id = -4`）除了 `notes_count = 26` 之外也没有标志位。

**③ 最关键：拿到密钥文件就能直接解，不需要输入任何东西。**

```python
from Crypto.Cipher import AES
key = open("files/miui_notes_secret_2", "rb").read()      # 32 字节
IV  = bytes.fromhex("fc9710a048cd7a2e775396ee4280face")
pt  = AES.new(key, AES.MODE_CBC, IV).decrypt(base64.b64decode(cipher))
```

本机 26 条私密笔记，一次全解，失败 0 条，PKCS7 padding 全部严丝合缝。如果密钥是从密码派生出来的，不知道密码在数学上不可能算出这个结果。

所以准确的说法是：**这是「打包保护」，不是「密码保护」。** 密码是门上的锁，钥匙挂在门背后的钉子上。真正防的是「别人借你手机翻一翻」「云端数据库泄漏」这两个场景，防不住拿到整个 `/data/data` 目录的人（root、全盘备份、取证镜像都算）。

---

## 4. IV 是怎么推出来的

固定 IV 本来是个设计缺陷，但它恰好让 IV 可以被反推。

CBC 第一块的加密公式：

```
C₁ = E(P₁ ⊕ IV)
```

只要知道第一块明文 P₁，就能用 ECB 单块解密反推出 IV：

```
D(C₁) = P₁ ⊕ IV     →     IV = D(C₁) ⊕ P₁
```

而这批便签里，**新格式笔记的第一块明文恒为** `<text indent="1"` —— 新格式开头固定带这个标签，数一数正好 16 字节，一个不多一个不少，刚好一块。

拿五条新格式的私密笔记各推一次，得到的 IV 完全相同，都是 `fc9710a048cd7a2e775396ee4280face`，那就确认是硬编码常量，不是随机值，也不存在密文里。

> 注意：只有新格式（`<text>` 开头）的才推得准。旧格式是纯文本开头，首块不是那个标签，推出来的是无意义的随机值。本机 26 条里 14 条得到同一个正确 IV，12 条是无意义值——所以按**出现次数最多**取，别按顺序取第一条。

脚本里留了这条路径，换版本后如果解出来是乱码，先跑：

```bash
python decrypt.py --guess-iv
```

它会打印从样本反推出的 IV，以及每个值出现的次数。多数票一致就直接用 `--iv` 传进去。

## 5. 顺带能看出来的设计问题

不是要挑刺，是换版本时要知道哪里可能变：

1. **IV 固定** → 相同明文块产生相同密文块。这批笔记开头都一样，所以密文开头也一模一样，肉眼就能看出来「这是私密笔记」。
2. **没有 MAC / AEAD** → 密文被改动了也发现不了，解密端不会报错，只会得到乱码。理论上是可延展的（malleable）。
3. **密钥和密文放在同一个目录** → 攻击者拿到目录就同时拿到两样，加密对「拿到设备数据」这一档威胁不构成阻力。
4. **`plain_text` 字段也存了密文** → 说明实现上是「整条记录加密」，不是「正文加密 + 元数据明文」。好处是没有明文残留，坏处是搜索索引在手机端也得解密后才能建。

反过来说，它也确实是加密而不是混淆：算法是标准 AES，密钥是真随机 32 字节，不是硬编码在 APK 里的字符串，也不是简单异或。

## 6. 换设备 / 换版本怎么复核

1. 拉一份新的 `files/miui_notes_secret_*`，看文件名编号有没有从 `_2` 变成 `_3`。脚本用 `glob` 匹配 `miui_notes_secret_*`，会自动挑排序最后一个。
2. 看密钥文件大小。32 字节 = AES-256；16 字节 = AES-128，脚本要改 `AES.new` 的 key 长度判断（现在只提示不阻断）。
3. 先跑 `python decrypt.py --sample 3`。解出来是中文就对了，是乱码就走 `--guess-iv`。
4. 如果 `--guess-iv` 推出多个不同的 IV，说明改成了随机 IV（通常会存在密文头部或数据库的另一列），这时候要按新结构去找，不能再用常量。

---

## 7. 一句话总结

```
密文 = base64( AES-256-CBC( 明文, key=secret_2 文件, IV=固定常量 ) )
```

密钥在应用私有目录里，和密文同一个盒子；密码只管界面入口，不参与运算。有 root 就是两条 `cp` 命令的事。
